## Changed in this round

### Settings on nodes
- **Show Question** is a setting now, next to Show Timer.
  - It can be set for the project, for a colour or for one node, like the
    other settings.
  - The question's text stays on the node; it's shown (and exported) only
    while the setting is on.
  - Projects from before keep their questions: a node that had one gets
    Show Question turned on.
- **Music** is a real setting now, like pause music.
  - The project's or a colour's Defaults can give every video music.
  - A node that overrides it shows it in pink, with an (x) that goes back
    to the defaults.
  - "None" in the list makes one node silent.
  - When it ends, loops, fades and pauses are part of the same setting.
- **New variables** start as whole numbers (Int).

### Screen designer
- **One kind of answer screen.** Choice and pause choice screens are now
  the same thing.
  - A node picks its screen with the Choice Screen setting.
  - Older projects: pause choice screens become choice screens named
    "Pause Choice Screen", and nodes that waited at the end keep using
    them.
- **One of each element.** The tray only offers what the screen doesn't
  have yet.
  - The exception is the new **Text** element, which can be added as often
    as you like. It shows your own text and can't be clicked.
- **Answer screens: under Background in the Design section.**
  - **Fade In:** when a video waits for an answer with no time to choose
    before its end, the screen starts fading in that long before the end.
  - **Fade Out:** after a pick, before the next video.
  - **Comes In:** fading, rising or growing.
  - **Effect** on the video behind: darken, blur, dark edges, or "answers
    breathe".
  - **Background:** a choice screen's background now goes *over* the
    video, so an image with see-through parts can frame it.
- **Behind** (above the stage, for answer screens): what the designer
  shows behind the screen.
  - Nothing.
  - The video player's frame, taken when you switch to the designer.
  - Any imported video, looping without sound. Import the nutria footage
    and pick it here.
  - This is only for designing and is never saved.
- **Pie layout:**
  - A Rotation setting, 0–180°.
  - The question in its middle now has a dark backing (a new built-in
    style, "Panel").
- **Styles:**
  - With an element selected, clicking a style in the right panel gives it
    that style.
  - "+ New Style" deselects the selected style.

### Problems in the story
- **Before exporting**, a warning lists the problems in the part of the
  story the origin reaches: videos missing, answers with text leading
  nowhere, logic that can't run, single answers. You can cancel or export
  anyway.
- **The Project section** has a Problems list. Clicking one shows its node
  on the canvas.
- **Nodes without a video** show the caution sign before "No video".
- **Logic nodes:**
  - A problem (e.g. a variable that doesn't exist) shows the caution
    triangle.
  - A warning (e.g. the result may be rounded) shows an exclamation mark
    in a circle.

### Project overview and selection
- **Shortest and Longest Way** now show the playing time and how many
  videos it takes, e.g. "2:31 · 5 videos".
- **Nodes:** "12 (9 in the main branch, 3 not reached)".
- **Edit > Select Nodes Outside the Main Branch** selects every node the
  origin can't reach.

### Keyboard
- **Arrow keys** no longer pan the canvas, and Ctrl+arrows no longer seek
  or change the volume, while you're typing in a text field.

### Player
- Plays the node's own music and question as the settings say.
- Draws the screen's background over the video.
- Fades answers in and out, early for videos that wait.
- Draws the effects, and turned pies.

### File formats
- **Project files:** now version 6. Older projects are upgraded when
  opened.
- **`.fmv` files:** new optional keys:
  - on answer screens: `fadeIn`, `fadeOut`, `entrance`, `effect`
  - on elements: `rotation`
  - a new `text` element kind

  Older Players ignore them.

## Feedback on the plans

### 1. Exporting a `.bin` with all media, and a Player set to open it

Good idea. Today a `.fmv` points at files by absolute path, so a story only
plays on the computer it was made on. A bundle fixes that.

- **Format:** an ordinary zip with nothing compressed (videos don't shrink
  anyway), with a new extension such as `.fmvpack`. It holds the `.fmv`
  plus a `media/` folder, with paths rewritten to point inside it.
  - Anyone can still open it to look inside.
  - Writing it is fast, since nothing is compressed.
  - It needs zip64 for stories over 4 GB, which is common for video.
- **Playing without unpacking:** media_kit (mpv) can't read straight from a
  zip. The clean way is for the Player to run a tiny web server inside
  itself (only reachable from the same computer) that serves byte ranges
  from the pack. mpv plays and seeks over HTTP without any extra copy.
  Unpacking to a temporary folder also works, but needs the disk space
  twice and a wait.
- **A Player set up for one story:**
  - **Version 1:** at startup, the Player looks for a pack next to its
    `.exe` and opens it. The Maker then gets **File > Export Standalone**:
    it copies a Player build (about 80 MB) and the pack into one folder,
    ready to zip and send.
  - **Later:** a custom window title and icon need the Windows resources
    changed, which tools like `rcedit` can do without rebuilding.
- **Licence:** the Player is GPLv3. Shipping it with a story is fine (the
  story is data), but the folder must include the licence and say where
  the source is. The Maker can add those files itself.
- **Not real protection:** a pack is easy to open. If authors want to keep
  people from taking the videos out, that's a separate (and never perfect)
  problem; I'd leave it out at first.
- **Effort:** medium. Mostly the packing, the small server in the Player,
  and the Export Standalone command. No change to how stories work.

### 2. Importing and exporting Twine stories

Worth doing, mainly as an **import**: writers can draft the branching in
Twine and then add the videos in the Maker.

- **Which format:** Twee 3 (the plain-text format Twine and Tweego use, with
  a published spec) for both directions. Twine 2's own `.html` files can
  also be read: inside is a simple list of passages.
- **How it maps:**
  - A passage becomes a branched video node: its title is the node's name,
    its text becomes a comment on the node, and its links
    (`[[Go left->Left]]`) become the answers, connected to their passages.
  - A passage with one link becomes a simple video node; one with none is
    an ending.
  - The start passage connects to the origin.
  - Twine keeps passage positions, so the layout carries over (scaled to
    node sizes).
- **Not a clean fit:** story-format code (Harlowe's `(set:)`/`(if:)`,
  SugarCube's `<<set>>`/`<<if>>`). Simple cases like `(set: $coins to it +
  1)` could become Math nodes and `(if: $coins > 3)` a Compare node.
  Anything else would be kept as text in the comment, and the import would
  report what it couldn't translate.
- **Export:** each node becomes a passage with links, the video file name
  in the text, and the logic written for one story format (I'd pick
  Harlowe, Twine's default). It's useful for proofreading the story in
  Twine.
- **Effort:**
  - **Import:** medium (parsing, mapping, auto layout, a report).
  - **Export:** smaller.
  - **Logic in both directions:** the costly part.

### 3. Audience voting on phones

A good fit for FMV, and doable. The main choice is where the "room" lives:

- **Room on the same Wi-Fi (start here):**
  - The Player itself runs a small web server.
  - It shows a QR code with its address and a room code.
  - Phones open a small web page (served by the Player, so nothing to
    install) and vote.
  - No internet or servers to pay for, and it works offline.
  - Windows asks once to allow the Player through the firewall.
- **Remote audience (streams):** this needs an online relay server that
  both the Player and the phones connect to (for example a small server on
  a free tier, or Cloudflare's Durable Objects). I'd design the messages so
  this can be added later without changing the phone page.
- **Rules to decide:**
  - **When voting runs:** during the choosing time.
  - **Endings:** with Pause on End, voting ends at a majority, or when a
    timer the host sets runs out.
  - **Ties:** settled by the node's default answer setting.
  - **Fairness:** one vote per phone (kept by the phone's browser),
    changeable until voting closes.
- **On screen:** each answer fills like a bar, or the pie slice grows, as
  votes come in, plus a vote count. The shared screens package would get
  the vote shares as part of its content, so the designer can preview it
  too.
- **Effort:**
  - **Same-Wi-Fi version:** medium-large (server, phone page, Player
    integration, designer preview).
  - **Online relay:** an extra hosted service to run and maintain.

### 4. The delay before the file dialog opens

Partly fixable. The delay is Windows' own file dialog starting up. The
first time it runs in a session it loads the shell, Quick Access, OneDrive
and network locations, and that can take a second or more. Things that do
help:

- **Open in a local folder:** start the dialog in the last folder used (or
  Videos). Opening on Quick Access, network drives or OneDrive folders is
  often the slowest part, because Windows asks each of them for their
  contents.
- **Show that something is happening:** a busy cursor, and the button
  disabled until the dialog is up, so the wait feels intended rather than
  broken.
- **Warm it up** by opening (and immediately closing) a hidden dialog
  shortly after the app starts. It's a hack: worth trying only if the
  first two aren't enough.
- **Drag and drop** from Explorer onto the library skips the dialog
  entirely (it already works).

I'd measure it first (time from click to dialog, first and second time).
If the second time is fast, it's the first-time start-up, and the folder
and warm-up ideas help. If both are slow, it's probably the folder it
opens in.
